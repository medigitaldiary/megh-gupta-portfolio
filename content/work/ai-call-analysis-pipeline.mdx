<Section variant="narrative" eyebrow="The problem" heading="Hours of calls, little structured feedback">

Two different workflow gaps collided on the RM team.

**Call quality was invisible.** Recordings sat in cloud storage after calls ended. Managers had no systematic way to review conversations, understand how RMs handled discovery and objections, or follow up with coaching. Spot checks happened; a consistent review process didn't.

**Customer objections weren't reaching marketing.** On calls, users raised concerns about pricing, trust, product complexity, and comparisons with fixed deposits — the exact language we needed to feed back into ads and landing pages. That signal was happening live in every call and reaching no one who wrote copy.

<Callout variant="insight">
The goal: turn daily recordings into structured coaching actions and customer-objection insights without adding manual work.
</Callout>

</Section>

<Section variant="deepDive" eyebrow="The solution" heading="From raw audio to action">

The pipeline runs as a scheduled nightly batch job. It picks up the day's recordings, transcribes them, scores them against a rubric, and delivers the output into Radar — the internal CRM where RMs and managers already work. Below is the full flow; play it through once to see the shape, or click any stage to inspect it.

<AiCallPipeline />

A scheduled job orchestrates the workflow. Sarvam handles speech-to-text. Claude Sonnet analyses transcripts and produces structured output. Radar becomes the operational destination for scores and tasks. The decisions behind each of those choices are in the next section.

</Section>

<Section variant="narrative" eyebrow="Decisions" heading="Why I built it this way">

Call-quality tooling wasn't on the engineering roadmap. Engineering was focused on the core platform — the right place for them to be. Rather than wait for capacity or pitch a dedicated sales-enablement platform (Gong, Chorus — both poor fit for cost, language, or the scope of this internal workflow), I built a v1 using API orchestration and a scheduled job. Vibe-coded end-to-end.

<Section variant="deepDive" eyebrow="The rubric" heading="Designing the call-quality rubric">

The pipeline's output is only as good as the definition of a good call. The rubric is what the LLM is actually scoring against. It evaluates six criteria.

<DataTable variant="data" caption="The six-criterion call-quality rubric">
  <thead>
    <tr>
      <th>Criterion</th>
      <th>What it evaluates</th>
      <th>What good looks like</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>Discovery</td>
      <td>Whether the RM understood the user before pitching.</td>
      <td>Asked about goals, horizon, prior investments; didn't jump into products in the first two minutes.</td>
    </tr>
    <tr>
      <td>Risk & return clarity</td>
      <td>How the RM explained the risk/return profile of the specific bond.</td>
      <td>Named the specific risk; put the return in the context of the lock-in; didn't oversell safety.</td>
    </tr>
    <tr>
      <td>Objection handling</td>
      <td>What the RM did when the user raised a concern.</td>
      <td>Acknowledged first, answered specifically, didn't deflect to a different product.</td>
    </tr>
    <tr>
      <td>Next steps</td>
      <td>Whether the call ended with a concrete action.</td>
      <td>Named date, named action, confirmed with the user — not "I'll send some options later."</td>
    </tr>
    <tr>
      <td>Pace & tone</td>
      <td>How the conversation felt from the user's side.</td>
      <td>Space between questions; adjusted to the user's confidence level; didn't rush closes.</td>
    </tr>
    <tr>
      <td>Empathy</td>
      <td>Signal that the RM heard the user as a person, not a lead.</td>
      <td>Reflected what the user said; met concerns on their terms before moving on.</td>
    </tr>
  </tbody>
</DataTable>

The overall score is a weighted roll-up across the six criteria. The weights are not disclosed on this page because they are still being tuned; the next revision may change them again.

### How the rubric changed between March and April

<Timeline variant="vertical">
  <Timeline.Event date="March 2026" title="Initial rubric — average reported 5.2 / 10">
    First-run rubric emphasised structural elements (discovery, next steps). Managers felt the scores didn't match their own coaching judgement on the same calls.
  </Timeline.Event>
  <Timeline.Event date="Between the two" title="Iteration based on manager feedback">
    Reweighted the parameters; added empathy and pace as distinct criteria; tightened the definitions used for objection handling so the LLM wasn't rewarding deflection.
  </Timeline.Event>
  <Timeline.Event date="April 2026" title="Revised rubric — average reported ≈ 6.0 / 10">
    Managers felt the revised scores were closer to their own read of the same calls.
  </Timeline.Event>
</Timeline>

<Callout variant="caution" eyebrow="Important caveat on the 5.2 → 6.0 change">
The rubric changed between these two measurements. The higher April average reflects a change in reported scores following rubric changes, not a validated improvement in real call quality. Reading it as "15% better calls" would be wrong. The right read is: the evaluation system now matches manager judgement more closely than it did in March.
</Callout>

</Section>

<Section variant="deepDive" eyebrow="Edge cases" heading="Making the output useful in real work">

A transcription-plus-summary workflow would have produced vague output no RM would act on. The practical decisions sat in the edge cases.

<StepGrid variant="parallel">
  <StepGrid.Cell title="Long or noisy recordings" eyebrow="Pre-processing">
    Trim long pauses, fillers, hold music, and repetitive confirmations before analysis. Keeps token and API cost aligned with the actual call content.
  </StepGrid.Cell>
  <StepGrid.Cell title="Unscoreable calls" eyebrow="Failure handling">
    When transcription fails or the audio is unusable, the call is tagged <strong>unscoreable</strong> instead of receiving a misleading number. Managers see the tag and know why there's no score.
  </StepGrid.Cell>
  <StepGrid.Cell title="Hinglish conversations" eyebrow="Language mix">
    No separate translation step. Claude handles the mixed-language transcript directly, which keeps meaning that would be lost in a translate-first pipeline.
  </StepGrid.Cell>
  <StepGrid.Cell title="Action-item quality" eyebrow="Prompt discipline">
    The prompt returns concrete tasks with deadlines — not generic "follow up with the user." The structured JSON schema enforces the shape.
  </StepGrid.Cell>
</StepGrid>

<Section variant="narrative" eyebrow="Rollout" heading="Earning trust before exposing scores">

Rollout was a product decision, not an afterthought. The team wanted to assess whether the AI scores were credible against manager coaching judgement before exposing them to RMs individually.

<StepGrid variant="sequence">
  <StepGrid.Cell title="Manager-only reports" eyebrow="Phase 1">
    Initial reports went to managers only. Individual scores were not shown to RMs in Radar. Managers compared the pipeline's scores against their own read of the same calls.
  </StepGrid.Cell>
  <StepGrid.Cell title="Rubric iteration" eyebrow="Between phases">
    Manager feedback fed the rubric revision described above. Reweighted parameters, added criteria, tightened definitions.
  </StepGrid.Cell>
  <StepGrid.Cell title="Radar integration" eyebrow="Phase 2">
    Scores and action items became available in Radar. RMs can see their own scores and tasks. Managers see the team view.
  </StepGrid.Cell>
</StepGrid>

Nothing here was a formal validation study — I don't have one and I'm not going to claim one. What I did have was manager judgement on specific calls, used as a sanity check before the pipeline's output started shaping individual coaching conversations.

</Section>

<Section variant="metrics" eyebrow="Results" heading="What changed and what the evidence shows">

Three different claims — kept separate on purpose.

### Workflow changes (shipped)

- Recordings now become structured call-quality scores and action items on a nightly cadence.
- Action items land in Radar as RM tasks with deadlines — part of the existing work queue, not a parallel surface.
- Managers have a systematic way to review call patterns across RMs instead of relying on spot checks.
- Customer objections surfaced on calls can inform marketing discussions downstream.

### What's still unvalidated

- Whether real call quality (as a user would experience it) actually improved between March and April.
- The agreement rate between AI scores and manager scores at the individual-call level.
- Downstream outcomes from the marketing feedback loop — whether specific objection themes led to specific copy changes, and whether those copy changes moved conversion.

Reporting these as open items is deliberate. The pipeline earned a place in the workflow; the counterfactuals didn't get measured.

<Section variant="reflection" eyebrow="Next" heading="What I'd improve next">

Three priority groups, honest about where each one sits.

- **Reliability.** Better retries, failure handling, monitoring, and alerts for transcription or analysis failures. Right now I'm the one who notices when a day drops silently.
- **Evaluation and feedback.** Let managers annotate or override scores inside Radar and feed those overrides back into the rubric review. The current loop is me reading manager feedback in Slack.
- **Operational hardening.** Cost and latency instrumentation (Sarvam latency, API spend by day), stronger governance for privacy and audit, secret management proper, backup and recovery. The things that separate "an internal v1 that works" from "a production system I'd hand to someone else."

Real-time analysis is the obvious next feature. I'd only build it when the user need actually calls for it — live assist is a different product than next-day coaching, and the complexity jump is real.

</Section>

<Section variant="deepDive" eyebrow="Under the hood" heading="Architecture and limitations">

### Known gaps I haven't closed yet

- Retries and robust error handling across the three API calls per recording.
- Monitoring and alerting (if a nightly run drops, I want a notification, not a Slack message from an RM the next morning).
- Scaling the orchestration beyond the current RM team's volume.
- Secret management properly centralised.
- Audit logging on every stage.
- Backup and recovery for the structured outputs.

Some of these controls may exist at a platform level that I haven't audited; I'm listing them as "I haven't verified they're there" rather than "they don't exist."

</Section>

<Section variant="narrative" eyebrow="What this enabled" heading="A pattern, not a one-off">

The project established a pattern for addressing internal workflows with LLMs + lightweight API orchestration, without needing a full engineering project from day one. The same pattern connects to other internal AI tools in flight: an internal assistant, a compliance workflow, a Deal QC tool, and MoEngage MCP workflows. Each one is small, each one is scoped to a specific operational gap, each one sits inside an existing surface rather than inventing a new one.

<Callout variant="learning">
The useful part of an AI workflow isn't the model. It's the quality criteria, the handling of edge cases, and the way the output fits into the team's existing work.
</Callout>
